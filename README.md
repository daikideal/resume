#### 不正検知つきログイン機能 (2026/06 ~ 2026/7)

```markdown
## 概要

自社の認証認可基盤を利用するコンシューマ向けプロダクトで発生した不正ログイン疑い事案を受け、未知端末からのログインを検知・通知する機能を設計・実装した。

## 担当

チームメンバー:

- エンジニア: 3名

役割:

- 課題整理・設計ドキュメント作成
- ログインAPI・端末列挙APIの実装

## 使用技術

- Go
- gRPC
- PostgreSQL
- Redis
- Google Cloud
  - Pub/Sub

## 課題

自社の認証基盤を利用するコンシューマ向けプロダクトにおいて、不正ログインの可能性がある事案が発生した。当時の認証フローでは、不正なアクセスがあってもユーザーが後から気づく手段がなく、多要素認証などの追加の安全対策も存在しなかった。

## 取り組み

- ログインした端末の情報を記録する"ユーザー端末"モデルを追加
- 未知の端末からのログインを検知する不正検知つきログインAPIを実装
  - 検知した場合はPub/Sub経由で通知サービスに連携し、メール/SMSでユーザーへ通知する
- ユーザー自身がログイン済みの端末に心当たりがあるか確認できるよう、端末列挙APIを実装
- ユーザーがログインに使用した覚えのない端末は登録を解除し、未知の端末に戻せるよう端末削除APIを実装

## 工夫した点

実装の過程で、端末列挙APIのレスポンスに含まれるユーザー端末の主キー(`id`)がログインCookieの値としてそのまま信頼されていることに気づいた。この`id`さえ入手できれば他人の端末になりすまして不正検知を回避できてしまう脆弱性であり、不正検知つきログイン機能の趣旨に背く挙動になっていた。

主キーとしての`id`とCookieに使う値を分離し、推測不可能な`token`カラムとして別途追加することで是正した。

## 成果

認証基盤としては、不正ログインを検知 + ユーザーが気づいてパスワードリセットを行うことで自分のアカウントを守れるような機能群を提供することができた。
```

#### Cloud SQL IAM認証移行 (2025/06 ~ 2026/05)

```markdown
## 概要

Cloud SQL for PostgreSQLに対し、アプリケーション・開発者・GitHub ActionsがIAM認証で接続でき、必要最小限の権限で操作されるようにした。

## 担当

チームメンバー:

- エンジニア: 3名

役割:

- 移行方針の策定
- DBロールの権限設計
- DBロールの権限管理の仕組み構築
- Terraformでのリソース管理
- アプリケーションおよびCIの実装

(全て個人で担当)

## 使用技術

- Go
- Terraform
- Google Cloud
  - Cloud SQL for PostgreSQL
  - IAM
  - Workload Identity Federation
- GitHub Actions

## 課題

GitHub ActionsからDBマイグレーションを実行できるようにする対応を進める中で、2つのリスクに気づいた。

1. GitHub ActionsからCloud SQLに認証・接続するために使用していたWorkload IdentityがSecret Manager上の任意のシークレットバージョンを取得できてしまう、権限が過剰な状態になっている
2. DBパスワードを取得して使用するが、パスワードがログに残らないようにマスキング処理をしている。しかしマスキング処理にミスがあったり、そもそもGitHub Actionsに脆弱性があったりするとDBパスワードが流出する恐れがある

また、推進していて気づいたことではあるが、パスワード認証運用においては全ての動線でCloud SQLのデフォルトユーザーとしてログインするようになっており、どのユースケースにおいても過剰な操作権限を有するようになっていた。

## 取り組み

DBのパスワード認証がSecret Manager上のパスワード管理に依存している以上このリスクは残り続けるため、DBのパスワード認証自体を廃止し、Cloud SQLのIAM認証へ移行することを決定した。

- IAM認証で利用できるDBロールにはDBの操作権限が一切ないことを知ったので、DBへの接続が必要なユースケースとそのユースケースで必要になる最小限の権限を洗い出し、DBロール一覧と権限のセットを設計
- Cloud SQLのIAM認証設定の追加と、DBロール一覧と権限のセットの管理をTerraformで実装
- DBオブジェクトのオーナーでないとオブジェクトの定義変更ができないため、これまでCloud SQLのデフォルトユーザーがDBオブジェクトのオーナーだったところを、マイグレーション用ロールがDBオブジェクトのオーナーになるよう変更
- パスワード認証を前提にした実装になっていたアプリケーションのDB接続処理、およびGitHub ActionsのDB接続処理を修正

## 工夫した点

DBオブジェクトのオーナー変更で顧客影響を出さない対策をした。

従来Cloud SQLのデフォルトユーザーがテーブルに読み書きを行えたのは、自らがテーブルのオーナーであることによる。
アプリケーションがデフォルトユーザーでDB接続し続けている状態で、DBオブジェクトのオーナーだけが変わると、アプリケーションがテーブルへの権限を失って読み書きができなくなり、プロダクトで不具合が多発しインシデントにつながる。

インフラ側の対応 → アプリケーション側の対応 の間で不具合を出さないために、マイグレーション用ロールのメンバ資格をデフォルトユーザーに与える設定を行った。
この設定により、デフォルトユーザーはメンバ資格を通じてオブジェクトのオーナー権限を持つことになり、引き続きデフォルトユーザーはテーブルの読み書きを行える。
インフラ側の対応だけ適用してもアプリケーションの動作に影響はないし、アプリケーション側のリリースに問題があってロールバックを行なっても従来通り動作して安全である。

## 成果

- アプリケーション・GitHub ActionsからDBへの接続ではパスワードを使わないようになり、DB認証情報の漏洩リスクを低減
- 開発者が問い合わせ調査などでDBを閲覧するときにも、Cloud SQL StudioなどでのIAM認証を利用した接続ができ、パスワードの取得・入力が不要になったので、日常運用の利便性の向上にも貢献
```

#### SAML/SCIM連携作業の自動化 (2025/04 ~ 2025/05)

```markdown
## 概要

従来、開発者が手作業で行なっていたSCIM/SAML連携作業をAPI経由で完結できる機能を設計・実装した。

## 担当

チームメンバー:

- エンジニア: 3名

役割:

- 業務シーケンスの整理・図の作成
- API設計の叩き台作成

## 使用技術

- Go
- Google Cloud
  - Identity Platform
  - Cloud Firestore
- HTML
- JavaScript

## 課題

前提として、自社プロダクトをSP(Service Provider)とした SAML SSO・SCIMプロビジョニング の機能はすでに認証認可基盤チームにより開発・運用されていた。運用される中で2つの課題が出てきた。

1. 開発当初は連携作業依頼はそれほど件数も多くなく特に困っていなかったが、営業の方針としてエンタープライズ向けの導入が増え、連携作業依頼が増加してきていた
2. また、対応しているIdPの一つであるOkta様より、OIN(Okta Integration Network)に弊社プロダクトを載せないかという旨の提案があった。連携手順をOINに掲載することになるが、手作業のままだと「弊社窓口まで連絡」という手順を載せることになり、開発者がボトルネックになってスケールしない懸念があった

## 取り組み

- SAML/SCIM連携の導入と運用をお客様の手で完結できるようにするための機能をリリース
  - Identity Platform Admin SDKを使用したSAMLプロバイダー作成API
  - SAML証明書更新API
  - SCIMシークレットの発行API
  - SCIMシークレット更新API
- API経由での連携作業をプロダクト側の開発者が体験できるよう、HTMLとJavaScriptで動くデモサイトを社内検証環境にリリース

## 工夫した点

プロジェクト始動当初はSAML/SCIM連携の**導入**だけが視野に入っていて、"SAMLプロバイダー作成API"と"SCIMシークレットの発行API"だけだったが、業務シーケンスの整理にあたってSAML/SCIM連携についてのユースケースを洗い出していると、過去に「証明書の期限が切れていたのでSSOに失敗した」という問い合わせがお客様より寄せられていたことを発見した。
その問い合わせは開発者が手作業でお客様のIdPのメタデータXMLより証明書の値を取得してIdentity Platformに入力することで対応したが、証明書の更新もAPI経由でできたほうがよりリードタイムを減らし、お客様に自走していただけるプロダクトになると考え、このタイミングでAPIとして実装することにした。

## 成果

認証認可基盤側の機能としては、SAML/SCIM連携を手作業なくAPI経由のみで完結させられるようになった。
2025年11月にプロダクト側でSAML/SCIM連携機能の実装が開始したため、プロダクトを通した市場投入の時期は未定。
```

#### Cloud SQLのサービス無停止アップグレード (2025/04 ~ 2025/05)

```markdown
## 概要

Cloud SQL for PostgreSQLをサービス無停止でアップグレード

## 担当

チームメンバー:

- エンジニア: 3名

役割:

- アップグレード方法の選定
- アップグレード作業

## 使用技術

- Cloud SQL Enterpriseエディション
- PostgreSQL

## 課題

家庭向け・オフィス向けスマートロックサービス共通の認証認可基盤のデータベースのアップグレードであるため、メンテナンス期間を設けることができない。

その他の前提:

- プライマリインスタンス×1、レプリカインスタンス×3
- アプリケーションはマイクロサービスで、データベースは3つに分かれている
- アプリケーションはGKEクラスタで稼働
- コネクションプールは使用していない

## 取り組み

Postgres組み込みの論理レプリケーション機能を使用して旧DBから新DBへデータを移行し、アプリケーションからの接続を切り替える作業を実施

## 工夫した点

3つの方法を検討した。

1. インプレースアップグレード
2. Google CloudのCloud DMS
3. Postgres組み込みの論理レプリケーション

1.は、プライマリをアップグレードするためにレプリカを停止する必要があり、プライマリも20分~1時間停止する。レプリカからアップグレードしてフェイルオーバーも考えたが、Postgresはバージョンが異なるインスタンス同士のレプリケーションをサポートしない。どうしてもサービス停止期間が発生するため不採用。

2.は、データベースごとに移行元インスタンスをプライマリ・移行先インスタンスをレプリカとして"接続プロファイル"を作成することでデータを同期することになる。しかしDMSの仕様上、移行元インスタンスから移行先インスタンスに対して同時に複数の"接続プロファイル"を作成することはできず、かつ移行先インスタンスのプロモート時にはデータ不整合を防ぐためにアプリケーションを停止することがGoogle Cloud公式より推奨されている。よって、作業期間が長引くうえにサービス停止期間が数回発生することになるため不採用。

3.は、自前でコマンドを実行して移行元・移行先インスタンス間のレプリケーションを組む手間がかかるものの、複数のデータベースを同時にデータ同期することができるので最終的な作業期間は長くはならない。さらに、レプリケーションを組んだあとはアプリケーション側のデータベース接続情報を移行元から移行先へと修正してローリングアップデートすればデータ不整合などは発生しない見込みが立ったため、採用。

検証環境で検証し、データ不整合やその他のトラブルも発生しないことを確認したので本番環境で決行したところ、503エラーが一時的に数件発生したのみで、問題なくアップグレードが完了した。

## 成果

Cloud SQL for PostgreSQLを、PostgreSQL 14からPostgreSQL 16へメンテナンス期間等を設けずにアップグレードすることができた。

学びとして以下のような知見を得た。

- PostgreSQLは、無停止でのメジャーバージョンアップに役立つ論理レプリケーションという機能が組み込みで存在する
- マイクロサービスごとにデータベースを分ける場合、特定のサービスのアップグレードが他のサービスに影響を与えないようにインスタンスごと分ける方がよい
```

#### パスキー認証機能の実装 (2023/10 ~ 2023/12)

```markdown
## 概要

自社の複数プロダクトを支える認証認可基盤にパスキー認証機能を実装

## 担当

チームメンバー:

- エンジニア: 3名

役割:

- 処理シーケンス図の作成
- プロトタイプの実装
- バックエンド・フロントエンドの実装

## 使用技術

- Go
- JavaScript (Web Authentication API)
- Firebase Hosting

## 課題

プロダクトへのログイン方法はID・パスワードによる認証がメインだが、パスワードはフィッシングの被害を受けやすく安全とは言えない。
UXを損ねずにパスワード以上の安全性を実現できるパスキー認証機能を認証認可基盤に実装し、プロダクトに提供することで顧客の安全で快適なサービス利用に貢献できると考えられた。

## 取り組み

- 選定したライブラリ(go-webauthn/webauthn)を使用して、パスキー認証のUXを体験できるプロトタイプを作成し、チームに共有
- Goを使用したバックエンドの開発
- HTML/JavaScriptを使用したパスキー認証のテストページの開発。テストページはFirebase Hostingでデプロイし、Datadogのブラウザテストでパスキー登録・認証ができるかを日次で確認
- VPoP・プロダクト側のマネージャー・デザイナーをお呼びし、テストページを使って、パスキーの必要性・パスキー認証のUXについて説明するデモを実施

## 工夫した点

認証基盤とプロダクトでドメインが異なることによりパスキー認証機能が提供できない問題に対し、リクエストから動的に RP ID を設定するアプローチを立案・実装し、解決した。

詳細はこちらのスライドで解説: https://speakerdeck.com/bitkey/challenges-and-solutions-for-passkey-authentication-implementation-in-authentication-and-authorization-infrastructure-supporting-multiple-brands-b71cf3bc-925d-441d-9c01-337f1bd26c73

　
デモにおいては、技術的な知識の非対称性に配慮して平易な言葉を選んだり、実際にパスキー登録~認証を体験してもらうことで、パスワード認証と比べてのメリットや、パスキーのUXについてイメージを持ってもらいやすくした。

## 成果

認証認可基盤の機能としてはパスキー認証を備えるに至った。

学びとして以下のような知見を得た。

- 複数の異なるブランド(ドメイン)のプロダクトを展開する企業の認証認可基盤にパスキーを実装する際は、RP IDの管理に工夫が必要である
```

#### ログ管理・分析基盤の構築 (2020/10 ~ 2021/5)

```markdown
## 概要

AIチャットサービスにおける、ログデータ保存方法の改善とログデータ分析基盤の構築

## 担当

チーム構成:

- CTO: 1名
- エンジニア: 1名

エンジニアとして、バックエンド及びインフラのライブラリ選定,設計,コーディング,テスト,運用/保守を担当

## 使用技術

- 言語
  - Ruby 2.6.6
- フレームワーク
  - Ruby on Rails 6.1.0
- データベース
  - MySQL 5.6
- クラウド
  - AWS
    - Amazon EC2
    - Amazon S3
    - Amazon Kinesis Data Firehose
    - aws-kinesis-agent
    - Amazon Athena
- その他
  - Docker
  - Logrotate
  - cron

## 課題

- APIサーバーのログは、AutoScalingのEC2インスタンス数増減によりサーバーごと破棄されてしまっていた
- 本番環境にて不具合や障害があった際、サーバーにSSHログインしてログを追うような面倒さがあったり、そもそも該当ログが既に破棄されてしまっている、といったようなことがあった

## 取り組み

- APIサーバーにaws-kinesis-agentをインストールし、Railsアプリケーションのログをトラッキングするよう設定。aws-kinesis-agentは一定期間ごとにログデータをAmazon Kinesis Data Firehoseを通じてS3バケットに送信するようにし、ログデータをEC2インスタンスの外側で保存
- 収集したログデータをクエリできるようにするため、Amazon AthenaからS3へと接続してログデータのテーブルを作成

## 工夫した点

- 当初はCloudWatchLogsを採用しようと考えていたが、当時のサービス運営状況においては約15GiB/日のログデータが発生していたので、CloudWatchLogsでログの収集・保存を行うとかなりの高額になってしまうことが判明。よって、より安価かつCloudWatchLogsと同等の難易度で実装可能なKinesis Data FirehoseとS3の組み合わせを採用
- Railsアプリケーションのデフォルトのログフォーマットだと検索性が低かったため、JSONフォーマットでロギングするよう変更。エンジニアメンバーに「不具合調査の際キーワードにするパラメータ」をヒアリングし、それをJSONのkey:valueとして出力するためのログフォーマッティングクラスを実装することで実現
- 運用開始直後、日付変更のタイミングでaws-kinesis-agentがログファイルのトラッキングに失敗する現象に悩まされたが、cronで実行されているLogrotateのローテーションモードがcopytruncateであり、このモードがaws-kinesis-agentでサポートされていないことを突き止め、createモードに修正することで解決

## 成果

不具合調査だけでなくアクセス元の集計等データ分析にも活用できるログ収集・分析基盤で、プロダクトの保守性向上と改善の両方に貢献。
例えば、「この案件でのボットはこの選択肢が一番押されている」というのをEMが調べられるようになって顧客への提案に活用されていた。
```
